# EVLVS Frontend & Backend Reviewer Updates

This document describes the updates to the front-end interface (`reviewer.html`, `login.html`) and backend reviewer controllers to resolve security vulnerabilities, role-based routing gaps, and file rendering issues. It builds upon the document review architecture described in `10.EVLVS-backend-document-review.md`.

---

## Step 1: Update Login Routing

In `login.html`, staff roles previously defaulted to `/applicant.html`. The routing logic in the login submission handler was updated to redirect `doc_reviewer`, `visa_staff`, and `manager` roles to `/reviewer.html`.

### `login.html` Diff

```diff
             switch (userRole) {
               case 'admin':
                 window.location.href = '/admin.html';
                 break;
+              case 'doc_reviewer':
+              case 'visa_staff':
+              case 'manager':
+                window.location.href = '/reviewer.html';
+                break;
               case 'applicant':
                 window.location.href = '/applicant.html';
                 break;
               default:
                 window.location.href = '/applicant.html';
                 break;
             }

```

## Step 2: Fix Data Leak in Pending Applications API

The original `getPendingApplications` function in `applicationReviewManager.js` fetched every field from both the `Application` and `User` models. This leaked the `photo_path` and `doc_path` values, which store the internal file path alongside the raw AES key and IV.

The query was trimmed using Sequelize's `attributes` options to exclude sensitive file path parameters and limit the user fields to essential display data (`first_name`, `last_name`, `email`).

### `applicationReviewManager.js` Diff

```diff
     const pendingApps = await Application.findAll({
       where: statusTarget,
-      include: [{ model: User }],
+      attributes: { exclude: ['photo_path', 'doc_path'] },
+      include: [{ model: User, attributes: ['first_name', 'last_name', 'email'] }],
       order: [['created_at', 'ASC']]
     });

```

(Note: File decryption in `viewDocument` continues to work properly because it reads the required path and key data directly from the database by `id`.)

## Step 3: Support Image Passports in Document Viewer

The `viewDocument` controller originally hardcoded the HTTP `Content-Type` header to `application/pdf` when servicing passport requests. When an applicant uploads an image passport (e.g., JPEG or PNG), this header causes rendering errors in the browser.

The handler was updated to parse the JSON string, inspect the stored extension, and set the appropriate MIME header dynamically.

### Controller Update (`applicationReviewManager.js`)

```javascript
// Decrypt and stream document (passport or photo)
const viewDocument = async (req, res) => {
  try {
    const { id, type } = req.params;
    const application = await Application.findByPk(id);

    if (!application) {
      return res.status(404).json({ success: false, message: 'Application not found.' });
    }

    const rawJsonData = type === 'passport' ? application.doc_path : application.photo_path;
    if (!rawJsonData) {
      return res.status(404).json({ success: false, message: `No ${type} record found.` });
    }

    // Inspect file extension inside stored metadata
    const fileMeta = JSON.parse(rawJsonData);
    const ext = path.extname(fileMeta.path).toLowerCase();

    const decryptedBuffer = decryptFile(rawJsonData);

    // Set dynamic Content-Type header
    if (ext === '.pdf') {
      res.setHeader('Content-Type', 'application/pdf');
    } else if (ext === '.png') {
      res.setHeader('Content-Type', 'image/png');
    } else {
      res.setHeader('Content-Type', 'image/jpeg');
    }

    return res.send(decryptedBuffer);
  } catch (error) {
    console.error('Error decrypting document:', error);
    return res.status(500).json({ success: false, message: 'Failed to decrypt and serve document.' });
  }
};

```

## Step 4: Prevent XSS with HTML Escaping

Because user input (`visa_type`, passport numbers) is rendered inside `reviewer.html` for staff accounts, untrusted text is escaped prior to insertion into the DOM to prevent Cross-Site Scripting (XSS).

### Frontend Escape Helper (`reviewer.html` & `applicant.html`)

```javascript
function esc(str) {
  if (!str) return '';
  return String(str)
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#039;');
}

```
