# Part 1 — Create an Application with Encrypted Documents

## Goal

The implementation uses one multipart request to submit application fields and two files:

- `photo` — applicant photograph.
- `passport` — passport/document file.

The uploaded files are kept in memory by Multer, encrypted with AES-256-CBC, written to the `uploads` directory, and represented in the existing `photo_path` and `doc_path` database columns as JSON strings containing:

- the encrypted file path;
- the encryption key;
- the initialization vector (IV).

## Dependency

Install Multer:

```bash
npm install multer
```

Create an `uploads` directory in the project root:

```text
uploads/
```

The server must have permission to write to this directory.

---

## 1. `routes/applicationRoutes.js`

Multer is placed between authentication and the controller so that the request is processed in this order:

```text
Verify JWT -> Parse multipart files -> Run application controller
```

Implementation:

```js
// routes/applicationRoutes.js
const express = require('express');
const router = express.Router();
const multer = require('multer');
const applicationManager = require('../controllers/applicationManager');
const authenticationManager = require('../middleware/authenticationManager');

// Keep files in memory so they can be encrypted before being saved to disk.
const storage = multer.memoryStorage();
const upload = multer({ storage });

// Expecting two specific file fields from the frontend.
const uploadFields = upload.fields([
  { name: 'photo', maxCount: 1 },
  { name: 'passport', maxCount: 1 }
]);

// POST /api/applications
router.post(
  '/',
  authenticationManager.verifyToken,
  uploadFields,
  applicationManager.createApplication
);

module.exports = router;
```

### Result

The route accepts a multipart/form-data request containing normal form fields plus `photo` and `passport` files.

# 2. `controllers/applicationManager.js`

The application controller performs four main operations:

1. Read application fields from `req.body`.
2. Use `req.user.userId` from the authenticated token.
3. Verify that the submitted first and last names match the authenticated user's profile.
4. Encrypt uploaded files and create the application record.

### Encryption helper

```js
// controllers/applicationManager.js
const crypto = require('crypto');
const fs = require('fs');
const path = require('path');
const { Application, User } = require('../models');

// Encryption helper function
const encryptAndSaveFile = (fileBuffer, originalName) => {
  if (!fileBuffer) return null;

  const algorithm = 'aes-256-cbc';
  const key = crypto.randomBytes(32); // 256-bit key
  const iv = crypto.randomBytes(16);  // Initialization vector

  const cipher = crypto.createCipheriv(algorithm, key, iv);
  const encryptedBuffer = Buffer.concat([
    cipher.update(fileBuffer),
    cipher.final()
  ]);

  const uniqueFileName = `${Date.now()}_${originalName}.enc`;
  const uploadPath = path.join(__dirname, '../uploads', uniqueFileName);

  fs.writeFileSync(uploadPath, encryptedBuffer);

  return JSON.stringify({
    path: `uploads/${uniqueFileName}`,
    key: key.toString('hex'),
    iv: iv.toString('hex')
  });
};
```

### Application creation

```js
const createApplication = async (req, res) => {
  try {
    const {
      first_name,
      last_name,
      visa_type,
      passport_number
    } = req.body;

    const user_id = req.user.userId;

    // 1. Verify profile names.
    const userProfile = await User.findByPk(user_id);

    if (
      !userProfile ||
      userProfile.first_name !== first_name ||
      userProfile.last_name !== last_name
    ) {
      return res.status(403).json({
        error: 'The provided name does not match the authenticated profile.'
      });
    }

    // 2. Encrypt and save files when supplied.
    let photoData = null;
    let docData = null;

    if (req.files && req.files.photo) {
      photoData = encryptAndSaveFile(
        req.files.photo[0].buffer,
        req.files.photo[0].originalname
      );
    }

    if (req.files && req.files.passport) {
      docData = encryptAndSaveFile(
        req.files.passport[0].buffer,
        req.files.passport[0].originalname
      );
    }

    // 3. Create application database record.
    const newApplication = await Application.create({
      user_id,
      visa_type,
      passport_number,
      photo_path: photoData,
      doc_path: docData
    });

    return res.status(201).json({
      message: 'Application created successfully with encrypted documents!',
      application: newApplication
    });
  } catch (error) {
    console.error('Application creation error:', error);
    return res.status(500).json({
      error: 'Failed to create application.'
    });
  }
};
```

# Frontend Requirement — Use `FormData`

Because the request now contains both text fields and files, the frontend cannot use:

```js
headers: {
  'Content-Type': 'application/json'
}
```

Instead, it needs to construct a `FormData` object and append the text fields and file inputs.

Example request pattern:

```js
const formData = new FormData();

formData.append('first_name', firstName);
formData.append('last_name', lastName);
formData.append('visa_type', visaType);
formData.append('passport_number', passportNumber);
formData.append('photo', photoInput.files[0]);
formData.append('passport', passportInput.files[0]);

const response = await fetch('/api/applications', {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${token}`
  },
  body: formData
});
```

Do **not** manually set `Content-Type` when using `FormData`. The browser needs to generate the multipart boundary itself.

# Part 2 — Return Application Data to the Applicant

The next addition exposes a protected GET endpoint that returns all application records belonging to the currently authenticated user.

## 1. Add `getUserApplications` to `controllers/applicationManager.js`

```js
const getUserApplications = async (req, res) => {
  try {
    const user_id = req.user.userId;

    const applications = await Application.findAll({
      where: { user_id },
      order: [['created_at', 'DESC']]
    });

    return res.status(200).json({ applications });
  } catch (error) {
    console.error('Fetch applications error:', error);
    return res.status(500).json({
      error: 'Failed to retrieve applications.'
    });
  }
};

module.exports = {
  createApplication,
  getUserApplications
};
```

### Endpoint

```text
GET /api/applications
```

The endpoint obtains the user ID from the authenticated JWT and therefore returns only records whose `user_id` matches the logged-in applicant.

# Review Findings / Potential Problems

## 1. The encryption key is stored beside the encrypted file metadata

This is the largest security concern in the current design.

The database value contains:

```json
{
  "path": "...",
  "key": "...",
  "iv": "..."
}
```

Therefore, someone who obtains both the database record and the encrypted file can also obtain the decryption key. The file is encrypted, but the key is not being kept separate from the ciphertext metadata.

For a development project or prototype this can demonstrate encryption successfully, but it should not be treated as a strong production key-management design.

A stronger production design would keep encryption keys in a protected key-management system or at least outside the application database, while storing only an identifier/reference in the application record.

## 2. `multer.memoryStorage()` has no file-size limit

The current configuration is:

```js
const upload = multer({ storage });
```

This means the uploaded files are held in RAM before encryption. Large or repeated uploads could consume significant memory.

For the current implementation, add an explicit size limit, for example:

```js
const upload = multer({
  storage,
  limits: {
    fileSize: 10 * 1024 * 1024
  }
});
```

That example limits each uploaded file to 10 MB.

## 3. Original filenames are used directly in the saved filename

The current filename is:

```js
const uniqueFileName = `${Date.now()}_${originalName}.enc`;
```

Using the client-supplied `originalName` is not ideal. It can contain unusual characters and may create awkward or unsafe paths depending on platform/filesystem behavior.

A safer approach is to generate a server-side random filename and retain the original filename separately as metadata if it is needed.

For example:

```js
const uniqueFileName = `${crypto.randomUUID()}.enc`;
```

## 4. `Date.now()` alone is not a robust unique identifier

Two uploads processed within the same millisecond could theoretically receive the same timestamp prefix. Including a UUID or random value makes filename generation safer.

## 5. `fs.writeFileSync()` blocks the Node.js event loop

The current code uses:

```js
fs.writeFileSync(uploadPath, encryptedBuffer);
```

This is acceptable for a small prototype, but asynchronous filesystem operations are preferable in a server application because synchronous disk I/O blocks the event loop.

## 6. There is no visible cleanup/transaction handling for partial failures

A possible failure sequence is:

```text
photo encrypted + written
        |
        v
passport encrypted + written
        |
        v
Application.create() fails
```

The files may remain in `uploads/` even though no application record exists.

Similarly, if the database record is created but a later operation fails, the system needs a strategy for maintaining consistency.

## 7. Name matching is an additional client-controlled check, not the main identity mechanism

The actual owner is determined through:

```js
const user_id = req.user.userId;
```

That is the important association. Checking `first_name` and `last_name` against values supplied by the frontend adds another validation layer, but it should not be considered authentication by itself because the client controls the submitted form fields.

## 8. The current GET endpoint returns the stored encryption metadata

`getUserApplications` returns the `Application` records directly. Since `photo_path` and `doc_path` contain the encryption key and IV, the GET response can expose those values to the browser.

That is likely **not desirable** for the final architecture.

A better design would return application information without exposing the encryption key, and provide a controlled backend endpoint for authorized document retrieval/decryption when the UI actually needs to display or download a document.

## 9. The implementation assumes the database column can hold the JSON string

The current design depends on `photo_path` and `doc_path` being large enough for the complete JSON string.

The supplied project reference says these columns are already `255` characters, but the actual `Application` model/database definition was not included in the material for this stage. Therefore, the exact column definition should still be verified in the project before relying on this assumption.

## 10. No file type validation is shown

The current route accepts the named file fields but does not show validation of MIME type or file contents.

For a visa system, the backend should eventually validate what types are accepted for each field, for example:

- photo: expected image types;
- passport: expected PDF/image types.

Client-side validation should not be treated as sufficient because the client can be bypassed.
