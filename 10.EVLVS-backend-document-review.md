# EVLVS Backend API — Document Review

This document describes how the backend APIs for the document reviewer were developed. The initial implementation focused primarily on providing the functionality required by the **document reviewer**. Support for the `visa_staff` and `manager` roles was added afterward so that the same unified API structure could be used by all privileged staff.

Three APIs were added:

1. **Get pending applications** — returns applications that require action from the authenticated user's role.
2. **Get a document** — decrypts and returns one file at a time. Each API call returns only one document, either the applicant photo or passport document. This keeps the implementation simple and allows the built-in HTTP file sending functionality to be used directly. The trade-off is that two API calls are required when both documents are needed.
3. **Update application status** — accepts an `approved` or `rejected` decision. The final application status is determined by the authenticated user's role, allowing all staff roles to use the same API endpoint.

The current workflow is:

```text
doc_reviewer:
  approved → Docs_Verified
  rejected → Docs_Rejected

visa_staff:
  approved → Staff_Reviewed
  rejected → Visa_Rejected

manager:
  approved → Manager_Approved
  rejected → Manager_Rejected
```

## Step 1: Add the Reviewer Routes

A new route module was added for the application review APIs.

First, import the authorization middleware and reviewer controller:

```js
const { verifyRole } = require('../middleware/authorizationManager');
const reviewerController = require('../controllers/reviewerController');
```

The allowed privileged roles are defined in one array:

```js
const allowedRoles = ['doc_reviewer', 'visa_staff', 'manager', 'admin'];
```

The three API calls are then added:

```js
// Both these calls go through two middleware:
// 1. Authentication of the JWT token
// 2. Authorization based on the user's role
// Applicant role is blocked because it is not in the array
router.get(
  '/pending-applications',
  verifyToken,
  verifyRole(allowedRoles),
  reviewerController.getPendingApplications
);

// Direct file streaming with URL params (:id and :type)
// :id is the application ID.
// :type is used to request either the passport or photo.
// Example:
// GET /api/applicationReview/documents/12/passport
router.get(
  '/documents/:id/:type',
  verifyToken,
  verifyRole(allowedRoles),
  reviewerController.viewDocument
);

// Allows staff to update the status of an application.
// Example:
// POST /api/applicationReview/update-application-status/12/approved
router.post(
  '/update-application-status/:id/:decision',
  verifyToken,
  verifyRole(allowedRoles),
  reviewerController.updateApplicationStatus
);
```

### Full `routes/applicationReviewRoutes.js`

```js
// routes/applicationReviewRoutes.js

module.exports = router;
```

## Step 2: Add the Authorization Middleware

A simple authorization middleware was added to check whether the authenticated user has one of the roles required to access the reviewer APIs.

The `verifyToken` middleware runs first and populates `req.user`. The `verifyRole` middleware then reads the role from `req.user` and checks whether it exists in the allowed roles array.

If the role is authorized, `next()` is called and the request continues to the controller. Otherwise, a `403` response is returned.

The flow is:

```text
Request
  ↓
verifyToken
  ↓
req.user populated
  ↓
verifyRole(allowedRoles)
  ↓
Controller
```

### Full `middleware/authorizationManager.js`

```js
// middleware/authorizationManager.js

exports.verifyRole = (allowedRoles) => {
  return (req, res, next) => {
    // req.user is populated by the verifyToken middleware that runs before this
    if (!req.user || !req.user.role) {
      return res.status(403).json({
        message: 'Access denied. Role information missing.'
      });
    }

    // Check if the user's role exists in the array of permitted roles
    if (!allowedRoles.includes(req.user.role)) {
      return res.status(403).json({
        message: 'Forbidden. You do not have the required permissions.'
      });
    }

    // Role is authorized, proceed to the actual route controller
    next();
  };
};
```

The applicant role is blocked because `applicant` is not present in:

```js
const allowedRoles = ['doc_reviewer', 'visa_staff', 'manager', 'admin'];
```

## Step 3: Add the Reviewer Controller

The reviewer controller exports the three functions used by the routes:

- `getPendingApplications`
- `viewDocument`
- `updateApplicationStatus`

There is also one internal helper function, `decryptFile`, which decrypts an encrypted document before it is sent to the client.

The controller also contains a guard clause in the status update function to ensure that the authenticated role has a valid status mapping before making a change.

### Full `controllers/reviewerController.js`

```js
const crypto = require('crypto');
const fs = require('fs');
const path = require('path');
const { Application, User } = require('../models');

// 1. Fetch applications based on user role
const getPendingApplications = async (req, res) => {
  const statusMap = {
    doc_reviewer: 'Submitted',
    visa_staff: 'Docs_Verified',
    manager: 'Staff_Reviewed'
  };

  const userRole = req.user?.role;

  // Block users without an authorized role
  if (!statusMap[userRole] && userRole !== 'admin') {
    return res.status(403).json({
      success: false,
      message: 'Unauthorized role'
    });
  }

  try {
    // Admin gets empty where clause (all records);
    // specific roles filter by mapped status
    const statusTarget =
      userRole === 'admin'
        ? {}
        : { status: statusMap[userRole] };

    const pendingApps = await Application.findAll({
      where: statusTarget,
      include: [{ model: User }],
      order: [['created_at', 'ASC']]
    });

    return res.status(200).json({
      success: true,
      count: pendingApps.length,
      data: pendingApps
    });
  } catch (error) {
    console.error('Error fetching applications:', error);
    return res.status(500).json({
      success: false,
      message: 'Server error'
    });
  }
};

// Helper: Decrypt file buffer
const decryptFile = (encryptedDataJson) => {
  if (!encryptedDataJson) return null;

  const { path: relativePath, key, iv } = JSON.parse(encryptedDataJson);
  const absolutePath = path.join(__dirname, '..', relativePath);

  if (!fs.existsSync(absolutePath)) {
    throw new Error('Encrypted file missing on storage.');
  }

  const encryptedBuffer = fs.readFileSync(absolutePath);

  const decipher = crypto.createDecipheriv(
    'aes-256-cbc',
    Buffer.from(key, 'hex'),
    Buffer.from(iv, 'hex')
  );

  return Buffer.concat([
    decipher.update(encryptedBuffer),
    decipher.final()
  ]);
};

// 2. Decrypt and stream document (passport or photo)
const viewDocument = async (req, res) => {
  try {
    const { id, type } = req.params;
    const application = await Application.findByPk(id);

    if (!application) {
      return res.status(404).json({
        success: false,
        message: 'Application not found.'
      });
    }

    const rawJsonData =
      type === 'passport'
        ? application.doc_path
        : application.photo_path;

    if (!rawJsonData) {
      return res.status(404).json({
        success: false,
        message: `No ${type} record found.`
      });
    }

    const decryptedBuffer = decryptFile(rawJsonData);

    if (type === 'photo') {
      res.setHeader('Content-Type', 'image/jpeg');
    } else if (type === 'passport') {
      res.setHeader('Content-Type', 'application/pdf');
    }

    return res.send(decryptedBuffer);
  } catch (error) {
    console.error('Error decrypting document:', error);
    return res.status(500).json({
      success: false,
      message: 'Failed to decrypt and serve document.'
    });
  }
};

// 3. Update application review status
const updateApplicationStatus = async (req, res) => {
  try {
    const { id, decision } = req.params; // 'approved' or 'rejected'

    // Status mapping based on reviewer role and decision
    const statusMap = {
      doc_reviewer: {
        approved: 'Docs_Verified',
        rejected: 'Docs_Rejected'
      },
      visa_staff: {
        approved: 'Staff_Reviewed',
        rejected: 'Visa_Rejected'
      },
      manager: {
        approved: 'Manager_Approved',
        rejected: 'Manager_Rejected'
      }
    };

    const userRole = req.user?.role;
    const roleStatuses = statusMap[userRole];

    if (!roleStatuses || !roleStatuses[decision]) {
      return res.status(400).json({
        success: false,
        message: 'Invalid decision or unauthorized role.'
      });
    }

    const application = await Application.findByPk(id);

    if (!application) {
      return res.status(404).json({
        success: false,
        message: 'Application not found.'
      });
    }

    application.status = roleStatuses[decision];
    await application.save();

    return res.status(200).json({
      success: true,
      message: `Application ${decision} successfully.`,
      data: application
    });
  } catch (error) {
    console.error('Error updating status:', error);
    return res.status(500).json({
      success: false,
      message: 'Failed to update application status.'
    });
  }
};

module.exports = {
  viewDocument,
  getPendingApplications,
  updateApplicationStatus
};
```

## Notes on the Implementation

### Unified status update API

The status update API uses the same endpoint for all privileged staff:

```text
POST /api/applicationReview/update-application-status/:id/:decision
```

The API accepts:

```text
approved
rejected
```

The authenticated user's role determines the actual status written to the database.

```text
Role          Decision    Resulting Status
------------------------------------------------
doc_reviewer  approved    Docs_Verified
doc_reviewer  rejected    Docs_Rejected
visa_staff    approved    Staff_Reviewed
visa_staff    rejected    Visa_Rejected
manager       approved    Manager_Approved
manager       rejected    Manager_Rejected
```

### Individual document retrieval

The document API returns one document per request:

```text
GET /api/applicationReview/documents/:id/:type
```

For example:

```text
GET /api/applicationReview/documents/12/photo
GET /api/applicationReview/documents/12/passport
```

The encrypted file is read from storage, decrypted using the stored AES key and IV, and then returned directly in the HTTP response.

### Role-specific pending applications

The pending application API uses the authenticated user's role to determine which status should be returned:

```text
doc_reviewer → Submitted
visa_staff   → Docs_Verified
manager      → Staff_Reviewed
```

An `admin` is currently allowed to access the endpoint and receives all applications because the query uses an empty `where` clause for that role.

### Current authorization scope

The authorization system currently focuses on the requirements of the document review workflow. Additional authorization rules may be needed later as more detailed staff permissions and administrative workflows are implemented.

### Current document type handling

The document endpoint currently selects the passport when `type` is `passport`; otherwise it uses the stored photo path. Additional validation of the `type` parameter can be added during later cleanup.

## Step 4: Test the Reviewer APIs with curl

Before testing, obtain a JWT belonging to a user with one of the permitted roles:

```text
doc_reviewer
visa_staff
manager
admin
```

Replace `REVIEWER_TOKEN` in the following commands with the JWT for the account being tested.

### 1. Fetch pending applications

```bash
curl -X GET http://localhost:5000/api/applicationReview/pending-applications   -H "Authorization: Bearer REVIEWER_TOKEN"
```

This should return applications matching the workflow status associated with the authenticated role.

### 2. Retrieve the passport document

```bash
curl -X GET http://localhost:5000/api/applicationReview/documents/1/passport   -H "Authorization: Bearer REVIEWER_TOKEN"   --output passport.pdf
```

The decrypted passport document is saved as `passport.pdf`.

### 3. Retrieve the applicant photo

```bash
curl -X GET http://localhost:5000/api/applicationReview/documents/1/photo   -H "Authorization: Bearer REVIEWER_TOKEN"   --output photo.jpg
```

The decrypted photo is saved as `photo.jpg`.

### 4. Approve an application

```bash
curl -X POST http://localhost:5000/api/applicationReview/update-application-status/1/approved   -H "Authorization: Bearer REVIEWER_TOKEN"
```

The resulting status depends on the authenticated user's role.

### 5. Reject an application

```bash
curl -X POST http://localhost:5000/api/applicationReview/update-application-status/1/rejected   -H "Authorization: Bearer REVIEWER_TOKEN"
```

The resulting status depends on the authenticated user's role.

### 6. Test unauthorized access

A JWT belonging to an applicant should be rejected because `applicant` is not present in the allowed roles array:

```bash
curl -X GET http://localhost:5000/api/applicationReview/pending-applications   -H "Authorization: Bearer APPLICANT_TOKEN"
```

Expected response:

```json
{
  "message": "Forbidden. You do not have the required permissions."
}
```

### 7. Verify the result directly in MySQL

After changing an application's status, the result can be checked directly in the database:

```bash
mysql -u root -p -e "SELECT app_id, user_id, status FROM Applications;" evlvs_db
```

This can be used to confirm that the status written by the reviewer API matches the authenticated user's role and decision.
